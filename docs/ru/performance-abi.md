# Производительность и ABI провайдера

[English](../en/performance-abi.md)

Сейчас работа сосредоточена на том, чтобы монитор виртуальных машин (VMM) тратил меньше времени на обслуживание гостевого исполнения. В первую очередь измеряем синхронные вызовы IOKit, обработку VMEXIT, повторное копирование состояния, обновление карты NPT и повторный захват глобальной блокировки QEMU (BQL). Уже полученные цифры собраны в [журнале замеров](../../evidence/reference-2026-11-17/README.md).

## Как устроен ABI сейчас

- Провайдер в ядре управляет состоянием SVM на CPU, VMCB и NPT, выполняет `VMRUN` и восстанавливает состояние хоста. При переключении состояния хост и гость используют отдельные буферы XSTATE в ядре. QEMU получает гостевой XSTATE через согласованную версию ABI состояния.
- QEMU отвечает за модель гостевого CPU, эмуляцию инструкций и устройства. Выходы, требующие эмуляции устройства или инструкций x86, обрабатывает QEMU.
- Диагностический CPUID/MSR probe и VM API разделены. У probe версия ABI 13. Для управления VM используется интерфейс версии 2 с возможностью согласовать версию 3 состояния x86. Объявления находятся в [amdvm_probe_abi.h](../../svm-kext/amdvm_probe_abi.h) и [amdvm_vm_abi_draft.h](../../svm-kext/amdvm_vm_abi_draft.h).
- RUN передаёт одним запросом состояние x86 и подготовленное событие. В результате возвращаются причина выхода и обновлённое состояние. Если провайдер объявляет поддержку shared RUN, QEMU может отобразить общую область для запроса и результата. Для каждого RUN по-прежнему нужен синхронный вызов IOKit. Ноябрьский архив E71D собран без опции shared RUN.

## Правила оптимизации

1. **Передавать состояние пакетом и версионировать расширения.** Передача регистров, инъекция события и вход в гостя входят в один запрос. Дополнительные режимы включаются после согласования возможностей. Для изменения существующего формата нужен совместимый путь.
2. **Ограничивать быстрый путь в ядре.** Провайдер может обработать локальный выход сам, когда понятна семантика и сохраняются изоляция гостя и восстановление состояния хоста. Перехваты остаются включёнными для операций, требующих модели устройств QEMU или ещё не проверенной замены. У гостя сохраняется запрет на прямой доступ к MSR и I/O хоста.
3. **Использовать крупные страницы NPT там, где позволяет память.** Для отображения на 2 МиБ или 1 ГиБ нужна выровненная, закреплённая и физически непрерывная память с одинаковыми правами и типом кэширования. Для MMIO, дыр и границ используйте более мелкие отображения или оставляйте адреса неотображёнными по необходимости. Крупные страницы здесь описаны как вариант оптимизации.
4. **Учитывать актуальность TLB при повторном использовании ASID.** Отслеживайте CPU и поколение. Учитывайте повторное назначение ASID, миграцию vCPU и изменение NPT перед повторным использованием трансляции. Адресная инвалидация применима там, где это допускают архитектура и время жизни отображения.
5. **Измерять прерывания и устройства отдельно.** Раздельно профилируйте APIC, инъекцию событий, доставку IRQ и уведомления virtio. Общие очереди и пакетные уведомления требуют проверки корректности и замеров под гостевой нагрузкой.

## Как измерять изменения

Фиксируйте образ гостя, прошивку, vCPU, RAM, фазу нагрузки и длительность замера. Для сравнения меняйте по одной опции. Вместе со скоростью работы или задержкой внутри гостя записывайте RUN/s, число выходов по классам, время вызовов провайдера, повторного захвата BQL, обновления карты памяти и прогресс гостя. Отмечайте, прошла ли штатная остановка. При SMP накопленное время по всем vCPU может превышать длительность прогона.

Используйте `perf-stats=on` для агрегированных счётчиков QEMU. На сравнительных замерах держите `trace-vmexit=off`. Повторяйте замеры внутри гостя с отключёнными счётчиками, чтобы проверить их влияние. Уменьшение отдельного счётчика показывает, где изменились затраты. Для вывода об ускорении нужно улучшение показателей внутри гостя. Сравнивайте с QEMU TCG или VirtualBox SVM там, где удаётся сопоставить конфигурацию и нагрузку. Отмечайте отличия в устройствах или прошивке.
